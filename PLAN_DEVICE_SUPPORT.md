# План адаптации audb для физических устройств и эмуляторов

Статус: начата реализация. Дата: 8 октября 2026 года.

Реализованы реестр `devices-v1.json`, add/update/remove/list/current/select, выбор цели и фактический deviceId в JSON, миграция emulator.json с резервной копией и атомарной записью. Старый devices.json предыдущей версии не изменяется. Добавлены общий DeviceTransport/DeviceBackend, OpenSSH/SFTP для телефона, независимые runtime и очереди по ID, переинициализация после обновления конфигурации и протокол CLI/daemon версии 8 с ограничением времени команды. Автоматическое повторение SSH команд удалено.

На телефоне проверены status, shell с сохранением stdout и ненулевого exit code, а также бинарный SFTP push/pull с пробелами, кавычками, обратным слешем и wildcard символами в имени файла. Независимость очередей и обновление QMP маршрута проверены интеграционными тестами с тестовым QMP сервером; реальный эмулятор в этой итерации не запускался.

Собран CLI версии 0.3.0 в `target/debug/audb`. В пользовательском реестре телефон зарегистрирован с ID `phone`; default остался `emulator`. Старая установленная команда audb не заменялась. Все 85 тестов workspace и Clippy с запретом предупреждений прошли при согласованных Rustc/Rustdoc/Clippy из stable toolchain. На телефоне отдельный счётчик подтвердил, что SSH команда с exit code 23 исполняется ровно один раз. Временные файлы проверки удалены.

Осталось в этапе 2: освобождение очереди между опросами длительных watch/monitor и уточнение диагностики SSH отказов до отправки. Служба, физические tap/swipe/screenshot и общий permission API реализованы; текст и клавиши реализованы; базовый сценарий подтверждён также на реальной VM AuroraOS-5.2.1.200/x86_64; расширенный паритет общих команд остаётся этапом 6. Последующие разделы описывают целевой объём; таблица текущих ограничений ниже фиксирует исходное состояние до этой итерации.

Добавлены `install_system_package()` и `setup_device()` в `audb-core/src/system_package.rs`, команды `package install-system` и `setup-device`. Общий установщик использует root `rpm -ivh --undefine=__transaction_validation` с предварительным --test; --upgrade выбирает -Uvh, --reinstall добавляет --replacepkgs, --check-only не устанавливает пакет. setup-device проверяет RPM Name audb-agent и использует тот же путь. Собранный пакет передаётся через --rpm; стандартный путь — packages/audb-agent.rpm рядом с audb, отсутствие файла возвращает NOT_FOUND.

Root bootstrap поддерживает SSH либо однократный пароль devel-su через stdin/скрытый запрос в терминале. Пароль не записывается в реестр и исключён из Debug и ответов. CLI/daemon протокол обновлён до версии 7. После установки проверяется RPM-база; при ошибке, обрыве или timeout транзакция не повторяется, временные файлы очищаются с best-effort обработкой отмены. Положительный dry-run объединённого подписанного StrongSwan RPM проверен на phone; устаревший runtime RPM отклонён до установки. После этой проверки собран и установлен audb-agent-0.3.0-3.aarch64.rpm. RPM запускает systemd службу, setup-device дополнительно проверяет готовность через клиент графической сессии.

Реализованы Rust служба `audb-agent`, клиент `audb-agentctl`, JSON протокол Unix socket и небольшой C++ Qt reader для геометрии Wayland. Служба создаёт постоянный uinput touchscreen, определяет единственную DRM панель и разрешает узкие input операции только root/членам input с проверкой SO_PEERCRED. Команды передаются по stdin SSH, пароль после установки не нужен. `tap`, `swipe` и направленные/edge/fast/long алиасы используют ориентированные координаты экрана. QMP эмулятора сохранён. Освобождение контакта при закрытии локального сокета клиента покрыто тестом; SSH/CLI timeout не гарантирует немедленной отмены — уже принятый жест может завершиться в пределах 4 секунд и 250 мс settle; действие не повторяется при неизвестном результате.

На phone по скриншотам подтверждены точные tap (открытие Помощи, выбор категории и страницы Экран в Настройках), горизонтальный swipe назад, edge-up на домашний экран, прокрутка списка Настроек вверх и вниз. Поворот экрана для ввода — 90°, геометрия 2000×1200, нативная панель 1200×2000. Остальные ориентации покрыты математическими тестами, но ещё не проверены на hardware. Первоначальные скриншоты проверки тачей получены исследовательским Lipstick/Flutter механизмом. Теперь физический audb screenshot реализован и проверен отдельно через новую службу. Сборка — `scripts/build-agent-rpm.py` через SDK sb2/rpmbuild; подписанный RPM и результаты находятся в target/agent-rpm и target/touch-evidence. Regular validator отвергает системную структуру пакета, поэтому применён согласованный developer RPM маршрут. Это не утверждение о production подписи или соответствии Regular application profile.

Реализован физический screenshot через `audb-agent`: root запрашивает Lipstick по пользовательской D-Bus шине, обычный `audb-agentctl` создаёт уникальный каталог в Pictures/Screenshots своего passwd home, ожидает полный PNG с корректными CRC и удаляет каталог до передачи изображения. UID берётся из SO_PEERCRED; root не читает пользовательские PNG. Служба использует ProtectHome=tmpfs с read-only BindReadOnlyPaths=/run/user. Размер ограничен 16 MiB, ожидание ограничено по времени. Обычные завершения, ошибки и обработанная отмена очищают staging; SIGKILL/авария могут оставить каталог. SSH/CLI timeout не гарантирует немедленной удалённой отмены.

На phone установлен подписанный `audb-agent-0.3.0-5.aarch64.rpm`; текущий подписанный артефакт также лежит в `target/debug/packages/audb-agent.rpm`. Проверены `--json screenshot --output`, сырой PNG stdout, фактическое декодирование PNG 2000×1200, тап в Помощь с изменившимся скриншотом, edge-up и три параллельных запроса захвата. Staging на устройстве очищен, служба работает без рестартов. JSON содержит format/bytes/width/height/output и deviceId; запись файла атомарна. Результаты находятся в target/screenshot-evidence. Эмуляторный QMP путь покрыт интеграционным тестом и использует уникальные host staging каталоги; реальный VM в этой итерации не запускался.

Реализован общий permission backend для телефона и эмулятора через службу и типизированный zbus D-Bus. Установлен подписанный `audb-agent-0.3.0-10.aarch64.rpm`, стандартный артефакт рядом с audb обновлён. Протокол CLI/daemon 8, локальный агент 3; permission запросы не требуют display, DRM или uinput. Неисправный input backend больше не препятствует запуску permission службы. Перед вызовами проверяются Aurora методы и их сигнатуры; UID берётся из SO_PEERCRED.

На phone проверены list, grant с --disable-prompt, объединение наборов, revoke, --all-requested, prompt enable/disable, reset, идемпотентность и ошибки неизвестного приложения/необъявленного разрешения. При отключении prompt служба переписывает ожидаемый набор, нейтрализуя автоматическую выдачу ОС. Запись проверяется чтением; частичная ошибка возвращает фазу и доступное before/after, replay запрещён. Permission worker ограничен 20 секундами, после timeout результат может быть неизвестен. Flutter secure-storage example после выдачи всех разрешений показал UI без диалога; приложение остановлено, начальные grants/prompt восстановлены. Артефакты — target/permission-evidence. Общий emulator путь проверен SSH интеграционным тестом без QMP; реальная VM остаётся отдельной проверкой.

audb должен управлять несколькими устройствами Aurora через одинаковые команды: ввод, скриншоты, приложения, файлы, диагностика и разрешения. Сначала добавляем реестр устройств и общий транспорт, затем системную службу и разрешения для телефона и эмулятора. Существующие сценарии эмулятора сохраняем.

Интеграция с `claude-in-mobile` выполняется отдельным этапом после адаптации audb. Будущие потребители включают CLI, skills и MCP. Поэтому основным внешним интерфейсом audb остаётся самостоятельный CLI с понятной справкой, стабильным JSON и явным выбором устройства. Для его использования не требуется MCP или знание внутреннего устройства службы.


Ввод текста и клавиш реализован: Rust/uinput для именованных key и фоновый Maliit plugin с небольшим C++ Qt extension для Unicode. Default — один commit всей строки, delay 0; text --stdin сохраняет UTF-8 и завершающий newline. При delay >0 следующий commit ждёт подтверждения текста и UTF-16 курсора. Параллельный ввод отклоняется; focus change, неполучение ожидаемого состояния или отмена клиента останавливают остаток. На телефоне проверено точное JSON-сравнение в Flutter, Qt-поле, обе раскладки, emoji/combining/CJK, multiline, editing keys и отмена. Раскладка/разрешения восстановлены, временная Flutter fixture удалена. Детали — [research/text-input/README.md](research/text-input/README.md). На эмуляторе общий маршрут проверен SSH-тестом и реальным сценарием на AuroraOS-5.2.1.200/x86_64. QMP fallback теперь отвергает неподдерживаемую строку до отправки любых символов.

Реализованы read-only `doctor` и `capabilities` с JSON reportVersion 1 и CLI/daemon протоколом 9 (локальный агент остаётся 3; RPM менять не требуется). Проверяются SSH/UID/архитектура, пользовательская шина, SFTP/OS version, агент, Maliit/focus, permission API, MCE, RuntimeManager, APM, настроенный root SSH и независимо QMP. Поля supported/available/ready отделяют реализацию от готовности; непроверенные операции получают null и NOT_PROBED. Doctor возвращает причины и подсказки, не выполняет исправлений. Outer ok означает получение отчёта, healthy означает отсутствие failed проверок. UI tree/clipboard остаются неподдерживаемыми. См. README, раздел Readiness and troubleshooting; результаты телефона — target/readiness-evidence. Прошли 85 тестов workspace и Clippy; QMP readiness проверен тестовым Unix socket сервером и реальной VM, включая последовательность screenshot → doctor → input.

Реальная VM AuroraOS-5.2.1.200/x86_64 проверена: установлен отдельный подписанный audb-agent-0.3.0-10.x86_64.rpm, работают permission grant/revoke/reset, повторный grant, отключение prompt перед launch, tap/swipe, Unicode/emoji/multiline и paced text, именованные key, PNG в stdout/файл. Содержимое Flutter-поля сравнивалось с JSON controller, capture не меняет поле/фокус. Doctor проходит. Исправлен конфликт сохранённого QMP соединения с disposable doctor probe на одноклиентском endpoint. Тест реестра изолирован от реального /tmp/audb/qmp.sock. Временное приложение и его RPM на VM удалены; VM и служба оставлены работающими. Первоначальные результаты — target/emulator-evidence, детали — README, Real emulator verification.

Устранены следующие ограничения, CLI/daemon протокол теперь 10, агент остаётся 3. QMP tap/swipe получают размер основного экрана перед каждым жестом через временный screendump; в память читаются только PNG header/trailer. Координаты проверяются до input events, алиасы рассчитываются относительно текущего экрана; doctor/capabilities публикуют QMP geometry. На VM подтверждены tap, точный ввод в выбранное поле, edge-up и возврат через cover при 360×800. Portrait/landscape, смена размера между жестами и ошибки geometry/границ проверены QMP socket тестами; смена реального разрешения VM ещё не проверена. Qt agent geometry 720×1600 не используется для QMP координат.

`package install` передаёт путь вместо массива байтов JSON и потоково загружает RPM через SFTP на обоих типах устройств. Проверяются RPM metadata/architecture, затем обычный APM вызывается один раз, и команда ожидает регистрацию нужных ID/version через GetPackage. `--timeout` задаёт ожидание регистрации (по умолчанию 60 секунд); общий command-timeout включает передачу и очередь. Совпадающая установленная версия возвращает changed:false. Успех очищает staging; при неизвестном результате после возможной отправки APM staging сохраняется для асинхронного installer, повторной установки нет. На реальной VM штатной командой установлен RPM 34,196,365 байт, проверены регистрация, очистка и повтор без изменений. Потеря ответа и большие RPM покрыты CLI тестами. Прошли 91 тест workspace и Clippy; evidence — target/limits-evidence. Расширенный аудит остальных файловых операций и этапа 6 остаётся открытым.

Недоступные операции возвращают конкретную причину через capabilities и код ошибки; успешный ответ означает выполненное действие.

## Текущее состояние и точки изменений

На `main` audb поддерживает только один эмулятор. Предыдущая поддержка телефона сохранена в `backup/physical-devices-v0.1.0`; она служит источником отдельных решений, но не заменяет проектирование нового общего backend.

Старый AudbBridge использовался только при первоначальной проверке тачей. Его исходники удалены из актуального дерева; они доступны в [истории Git](https://github.com/KotDath/audb/tree/190bbaa/app/AudbBridge). Рабочий backend физического устройства — `audb-agent`, эмулятора — QMP.

| Файл или модуль | Текущее ограничение | Изменение |
| --- | --- | --- |
| `audb-core/src/config.rs` | Один `EmulatorConfig` в `emulator.json` | Версионированный реестр и конфигурация по типу устройства |
| `audb-client/src/main.rs` | Только ID `emulator`, JSON содержит этот ID, add и remove не работают | Разрешение ID, команды реестра, фактический ID в ответе |
| `audb-client/src/daemon.rs` | Один `EmulatorBackend` под общим mutex | Реестр runtime и отдельная очередь операций на устройство |
| `audb-protocol/src/types.rs` | В запросе нет device ID | Явная цель запроса, сроки выполнения и обновление версии протокола |
| `audb-core/src/transport.rs` | SSH привязан к эмулятору и повторяет команду после любой ошибки | Общий SSH транспорт и правила повторов с учётом результата отправки |
| `audb-core/src/backend.rs` | Общие операции и QMP объединены | Общие сервисы Aurora и отдельные backend для устройств |
| `audb-core/src/input.rs` | QMP, размер 360 на 800, пропуск неподдерживаемых символов | Геометрия устройства, общий контракт ввода, явная обработка текста |
| `audb-core/src/screenshot.rs` | QMP, окно хоста, Lipstick с общими именами временных файлов | Захват по capabilities, координаты экрана и уникальные временные файлы |
| `app`, `appdata`, `system`, `display`, `diagnostics` | Принимают `EmulatorTransport` | Используют общий транспорт и нужные привилегированные операции |

## Целевая архитектура

```text
Человек, CLI, skill или MCP клиент
                 |
           audb CLI
                 |
       локальный daemon audb
                 |
       device ID -> DeviceRuntime
                 |
      общие сервисы Aurora
         /               \
 EmulatorBackend     PhysicalBackend
   SSH + QMP          SSH + agent
   + agent
                 |
      audb-agentctl через SSH
                 |
     локальный Unix socket устройства
                 |
      системная служба audb-agent
```

`DeviceRuntime` содержит параметры конкретного устройства, его соединения, сведения о возможностях и очередь действий. Общие операции приложений, файлов и диагностики не зависят от QMP. Backend выбирает реализацию ввода и захвата экрана внутри audb.

`audb-agent` поставляется RPM пакетом с systemd unit и небольшим клиентом `audb-agentctl`. Служба выполняет необходимые привилегированные операции, а действия в пользовательской сессии выполняются с её UID и D-Bus окружением. Получение экрана и ввод текста не считаем автоматически решёнными наличием root.

Служба используется на телефоне и эмуляторе для новых общих возможностей, включая разрешения. Базовые существующие команды эмулятора через QMP продолжают работать без установленной службы. Отсутствие службы отключает только зависящие от неё возможности.

## Интерфейс CLI для человека и агента

Команды реестра, select, --device и стабильный JSON уже реализованы. Команды doctor и capabilities реализованы; отдельный интерфейс agent остаётся следующим этапом. Permission list/grant/revoke/reset/prompt реализованы. Screenshot уже возвращает PNG в stdout без --output; --json требует --output. Для существующих команд сохраняем совместимость, где это возможно.

```bash
# Путь к существующему SSH ключу пользователь подставляет при регистрации.
audb device add --id aurora-phone --name "Aurora phone" \
  --kind physical --host 192.168.2.44 --port 22 \
  --user defaultuser --key /path/to/ssh-key

audb --json device list
audb --device aurora-phone --json status
audb --device aurora-phone --json doctor
audb --device aurora-phone --json capabilities

audb --device aurora-phone tap 180 400
audb --device aurora-phone text "Привет, Aurora"
audb --device aurora-phone screenshot > screen.png
audb --device aurora-phone --json screenshot --output screen.png

audb --device aurora-phone --json permission list ru.example.App
audb --device aurora-phone --json permission grant ru.example.App UserDirs
audb --device aurora-phone --json permission revoke ru.example.App UserDirs
audb --device aurora-phone --json permission reset ru.example.App
audb --device aurora-phone --json permission grant ru.example.App --all-requested --disable-prompt
audb --device aurora-phone --json permission prompt ru.example.App --disable
```

Правила внешнего контракта:

- `--device` относится ко всему вызову и передаётся до исполнителя команды. Команда не меняет глобальное выбранное устройство.
- `select` сохраняет удобный default для ручной работы. Без явного ID используем сохранённый default, затем единственное зарегистрированное устройство; при неоднозначности возвращаем `DEVICE_REQUIRED`. Неизвестный ID возвращает `DEVICE_NOT_FOUND`.
- ID постоянный и независим от IP адреса. Обновление адреса не меняет ID. Поддерживаем несколько записей обоих типов.
- Реестровые команды работают с отключёнными устройствами. Список содержит зарегистрированные устройства и различает состояние SSH, службы и QMP.
- В режиме `--json` stdout содержит один документ. Прогресс и диагностика идут в stderr. Ошибка сопровождается ненулевым exit code и машинным кодом.
- Бинарный режим возвращает только байты в stdout. Для него ошибки идут в stderr; `--json` требует `--output`. JSON режим скриншота через `--output` возвращает путь, формат, число байт и геометрию.
- JSON содержит версию схемы, фактический `deviceId` и `data` либо `error`. Для команд без цели и ошибок до выбора устройства `deviceId` равен `null`.
- Публичную JSON схему и внутренние протоколы CLI с daemon и daemon со службой версионируем отдельно. Несовместимость возвращает понятную ошибку до выполнения действия.
- `capabilities` различает поддерживаемую возможность и её текущую готовность, сообщает причину недоступности. `doctor` предлагает конкретное исправление.
- Таймаут и отключение клиента ограничивают длительность работы. Повторный запуск после потери связи не должен автоматически повторять tap, text, установку или произвольный shell с неизвестным результатом.
- Текст, пути и параметры передаются структурированно. Удалённый shell используется только там, где он необходим; команда `shell` явно предназначена для выполнения shell строки.

Справка и примеры входят в результат адаптации audb: короткая последовательность регистрации, проверки, установки службы и действий. Она должна быть пригодна для включения в будущие skills без знания QMP и D-Bus.

## Подключение телефона и подготовка возможностей

Для простого подключения предлагается дополнительная короткая форма регистрации, совместимая с полной формой через параметры:

```bash
audb device add defaultuser@192.168.2.44 --id phone
audb --device phone --json doctor
audb --device phone agent install
audb --device phone --json capabilities
audb --device phone tap 180 400
```

Порядок авторизации: явный `--key`, затем настроенный SSH профиль и SSH agent либо явно выбранные стандартные ключи. Поддержку этих источников нужно реализовать в транспорте; текущий russh код сам по себе не использует всю конфигурацию системного SSH. Удобный сценарий должен воспроизводить уже работающий SSH доступ без повторного ввода пароля при каждом действии.

Регистрация создаёт запись даже для временно отключённого устройства. `doctor` отдельно проверяет SSH, UID, архитектуру, пользовательскую сессию и версии компонентов. Установка службы является отдельным действием. После неё доступные возможности проверяются повторно: устройство может иметь рабочие shell и файлы при ещё недоступных input или screen.

Первый прототип должен закрыть четыре результата: tap меняет ожидаемый элемент, swipe прокручивает список и выполняет системный жест, screenshot даёт PNG в той же системе координат, русский текст попадает в активное поле. Результаты проверки тачей и команды воспроизведения сохранены в [исследовании физического input](research/physical-touch/README.md). На текущем устройстве DRM modes сообщает панель 1200×2000, скриншот имеет размер 2000×1200, а физические evdev оси уже имеют диапазоны X 0…1999 и Y 0…1199. Для точного uinput tap потребовались виртуальные оси X 0…1199, Y 0…1999 и Qt orientation 2. Размеры разных backend нельзя смешивать. UI дерево отложено и не является условием первой поставки.

## Этап 2 Общий транспорт и исполнение

1. Выделить `DeviceTransport` и общий код Aurora из `EmulatorTransport` и `EmulatorBackend`. Сохранить текущие SSH, SFTP и QMP реализации, меняя их зависимости поэтапно.

После выбора работающих механизмов:

1. Добавить Rust компоненты `audb-agent` и `audb-agentctl`, общий типизированный протокол и сборку RPM для архитектур тестовых телефона и эмулятора.

Поэтому первый рабочий постоянный процесс проверять после установки подписанного пакета; отдельно подтвердить прохождение проверки исполняемого файла при запуске.
2. Создать systemd unit с runtime каталогом, перезапуском после сбоя и журналированием. Готовность проверять запросом к службе, а не только `systemctl is-active`.
3. Согласовать доступ к Unix socket с авторизованным пользователем устройства и проверкой peer credentials. UID брать из реальной конфигурации пользователя; не фиксировать `100000`.
4. Передавать запросы к `audb-agentctl` через stdin SSH канала. Не включать JSON, текст или пароли в состав удалённой shell команды.
5. Привилегированные действия оформить отдельными командами службы. Операции пользовательского D-Bus выполняются в контексте активной сессии. `shell --root` описать как отдельную capability с явно настроенным способом доступа.
6. Реализовать `agent status`, `agent install`, `agent upgrade` и `agent remove`, проверку версии и восстановление после обновления. Изменения пакетов выполняются только явными командами установки или обновления.

9. Проверить чистую установку, обновление, удаление и запуск после перезагрузки. Выбрать режим запуска службы на этапе упаковки, исходя из минимальных требований для доступности команд.

Критерий завершения: audb обнаруживает и проверяет службу на обоих типах устройств; версия протокола согласована; привилегированное действие выполняется без запроса пароля после настройки; реальные механизмы экрана и ввода подтверждены.

## Этап 4 Разрешения на обоих типах устройств

Исследование на телефоне завершено: [API, хранение и проверенная семантика Aurora](research/permissions/README.md). SetShowPrompt из 1 в 0 автоматически выдаёт все объявленные разрешения, из 0 в 1 очищает grants. SetGrantedPermissions при prompt 1 отвечает успешно, но сохраняет пустой набор. Поэтому порядок и связь операций ниже уточнены по проверке на устройстве; CLI permission list/grant/revoke/reset/prompt реализован; подробные примеры и контракт находятся в README.md.

Используем системный D-Bus `org.sailfishos.sailjaild1`, путь `/org/sailfishos/sailjaild1` и интерфейс `org.sailfishos.sailjaild1`. На исследованном телефоне обнаружены `GetAppInfo`, `GetGrantedPermissions`, `SetGrantedPermissions`, `GetShowPrompt` и `SetShowPrompt`. На эмуляторе и других версиях ОС проверяем доступность и сигнатуры до объявления capability.

1. Добавить модуль разрешений с типизированными D-Bus вызовами через службу. Разделить инициализацию permission API и экрана/uinput: для разрешений не требуются Qt геометрия и DRM панель. Разрешать приложение по его sailjail application ID, показывать этот ID в app metadata; не считать RPM package name всегда тем же идентификатором.
2. `permission list` возвращает UID, объявленные разрешения, сохранённые grants, состояние показа диалога и доступные сведения о разрешениях, автоматически предоставляемых ОС. Не смешивать grants с эффективным доступом.
3. `grant` читает текущий набор и добавляет конкретное объявленное разрешение. При prompt 1 требуется явный --disable-prompt; без него возвращать PROMPT_ENABLED до изменений. С флагом сначала отключить prompt, затем записать объединение исходных grants с выбранными разрешениями и прочитать результат. `SetGrantedPermissions` заменяет весь набор, поэтому запись одного элемента без объединения запрещена.
4. `revoke` удаляет конкретное разрешение из сохранённого набора. Если ОС предоставляет его независимо от пользовательских grants, отражать ограничение; не сообщать, что эффективный доступ гарантированно отозван.
5. `--all-requested` получает Permissions через `GetAppInfo`. Не брать список из заранее захардкоженных имён.
6. Изменение prompt должно быть явным: grant без --disable-prompt его не меняет. Отдельный `prompt --disable` сохраняет исходные grants: после SetShowPrompt(..., 0) вернуть исходный массив, чтобы нейтрализовать автоматическую выдачу всех разрешений ОС. `prompt --enable` использует SetShowPrompt(..., 1), который на проверенной Aurora очищает grants; отражать это в справке и before/after.
7. Для `reset` принять семантику: SetShowPrompt(..., 1), пустой пользовательский набор и проверка обоих значений, без очистки данных приложения. Это состояние проверено на тестовом приложении телефона; на других версиях проверять совместимость. Не изменять глобальные или обязательные разрешения ОС.
8. Выполнять read modify write последовательно для пары UID и application ID. Проверять состояние после записи, возвращать before и after, включая частичный результат, если второй шаг reset завершился ошибкой. Изменения извне процесса могут потребовать повторной сверки состояния.
9. Неизвестное приложение, необъявленное разрешение, отказ D-Bus, несовместимая служба и неуспешная проверка возвращают разные машинные ошибки.

Критерий завершения: на телефоне и эмуляторе установка тестового приложения, выдача разрешений и запуск проходят без диалога после явного отключения prompt. Одиночный grant сохраняет другие grants; revoke и reset подтверждаются чтением состояния и повторным запуском приложения. При необходимости перезапуска уже работающего приложения сообщаем это в результате.

## Этап 5 Ввод и скриншоты

1. Реализовать input backend физического устройства через проверенный механизм службы. Не фиксировать путь `event3` или другой номер: определять устройства ввода и их диапазоны, отдавать предпочтение uinput, когда это подтверждено прототипом.
2. Сохранить QMP для эмулятора; убрать константы геометрии из общего интерфейса. Различать геометрию панели, PNG и осей input backend; получать текущую ориентацию из графической сессии. Координаты CLI относятся к текущему экрану устройства и совпадают с полученным PNG.
3. Добавить явные double tap и long press, общие клавиши и существующие варианты swipe. Длительность жеста и ожидание стабилизации экрана описать отдельно.
4. Реализовать выбранный ввод Unicode на обоих типах. Если механизм недоступен, проверять строку до отправки и возвращать ошибку; не пропускать символы с успешным статусом.
5. Перенести подтверждённый Flutter kit механизм Lipstick D-Bus в службу и проверить его в нужной сессии. ScreenGrab исследовать как альтернативу при недоступности Lipstick. На эмуляторе сохранить QMP захват. Автоматический fallback не должен возвращать изображение с рамкой окна и иной системой координат.
6. Добавить размеры, ориентацию и сведения о выбранном backend в информацию об экране и метаданные скриншота. Проверять PNG и использовать уникальные пути временных файлов на хосте и устройстве.
7. При ошибке, отмене или обрыве гарантировать отпускание активных touch и key событий настолько, насколько позволяет backend; для службы предусмотреть восстановление состояния ввода после исчезновения клиента.
8. Закрытый или недоступный экран описывать в status и ошибке. Не обещать автоматическое снятие блокировки, требующей PIN.

Критерий завершения: один сценарий tap, swipe, русский текст, screenshot работает на обоих типах. Проверены разные размеры экрана, ориентация и отмена жеста; нет потерянных символов и зависшего нажатия.

Критерий завершения: все согласованные общие команды имеют проверенное поведение или конкретное объяснение ограничения. Из документации можно настроить телефон и эмулятор и выполнить агентский сценарий без чтения исходного кода.
